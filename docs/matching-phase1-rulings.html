What a ruling is, and why you are seeing them now

A plan running autonomously cannot stop and wait for you on every conflict. The process I followed requires me to decide, record the decision with its reasoning and its cost if wrong, and keep going — then surface the whole list at the end.

Each ruling below was a real fork: the spec said one thing and the plan another, or a reviewer found something the plan mandated, or an implementer hit an instruction that could not be carried out. Every one is reversible. The ones worth your attention are the handful where a different answer would produce a materially different product, and those are first.

One pattern is worth naming before the list. The defects that survived longest were never syntax errors or failing tests. They were pieces that each read correctly, compiled, and passed their own tests — and were wrong only where two of them met. Several rulings below exist because a reviewer or an implementer noticed a seam rather than a bug.

Five caught while building

These surfaced during the eighteen task reviews. Each would have shipped a system that looked correct and behaved wrongly on real citizen data.

R25 The column storing a human's verdict used the wrong vocabulary my defect

MatchDecision.decision was typed with the candidate-state enum (auto_match / grey / confirmed / rejected) while every human-facing path submitted a verdict (match / no_match). Four separate tasks were each internally consistent, each compiled, each passed its own tests.

Failure scenario The first time a steward records a real verdict, the scoring join matches nothing. Every human decision becomes invisible, the review queue re-asks every question forever, and no error is raised anywhere.

If the ruling is wrong: it is not — this was a straightforward contract mismatch. The cost was four tasks of latency before it surfaced.

R20 A trigram pass's pair projection is a lower bound, not an estimate scale

The safety gate that refuses impossibly large jobs computed pairs as sum(n·(n−1)/2) — which counts exactly equal keys. A trigram pass proposes every pair above a similarity threshold, a strict superset.

Failure scenario On a near-unique key — a surname, a phone number, precisely what trigram passes are for — the histogram is almost all singletons, so the projection reads near zero. The gate clears the job, and the query it clears is a quadratic self-join that never returns. The gate reads safe on the one query it exists to stop.

If wrong: the fix was honesty rather than a better formula — the projection is flagged inexact and every consumer must render "at least N". Properly estimating a similarity join needs sampling; that is phase-4 work.

R43 Undo must retract a verdict, not assert the opposite governance my defect

My plan specified that the review queue's undo key "re-submits the opposite decision". A stored verdict is not advisory: scoring honours it regardless of score and maps no_match to rejected in every future run.

Failure scenario A steward fat-fingers m and presses undo. The system permanently records, in their name, a certification that two people are not the same person. "I have no opinion" and "these are different people" are different claims, and a keystroke slip converted one into the other. It also threw a constraint violation on every undo.

If wrong: phase 2 may want a soft retraction with an audit trail instead of a delete. The pair-level unique constraint already makes this table a record of current verdicts rather than an append-only log, so the fix follows the existing grain.

R31 · R32 · R33 Deleting a project destroyed the authority but kept every act governance my defect

No foreign key constrains project_id on any child table, so a hard delete does not fail — it silently orphans runs, decisions, clusters and crosswalk rows. The project row is what carries the lawful basis and the accountable data owner.

Failure scenario Deletion removes the recorded justification for copying citizen data while retention deliberately keeps the results forever. Orphaned crosswalk rows stay live and joinable while pointing at a project that no longer exists. My first fix (R31) defined what a soft delete stores and never what it prevents — so a "deleted" project still started runs and materialized fresh citizen data (R32). Editing was the same hole: widening the column allow-list after a run retroactively changes the legal boundary of what the system was permitted to copy, with nothing recording that it moved (R33).

If wrong: a field-level history table is the better long-term answer and is phase-4 work. Immutability-from-first-run is the cheap rule that closes it now.

R7 The guard keeping personal data on-premises failed open governance my defect

I specified the check as a block-list of known cloud providers. The provider column is an unconstrained varchar(50) with no database enum or constraint.

Failure scenario Any value not on the list — a new provider added to the enum later, or a typo like locall — returns normally and is treated as local. The spec's own wording was "local, or custom pointed at a private host, only"; the enumeration I wrote undermined the word that carried the rule.

If wrong: an allow-list is strictly narrower. The only risk is a legitimate future local provider being refused until it is added — which fails closed and is immediately visible.

What only the whole-branch review could see

Eighteen task reviews passed. The broad review then found two Criticals that no task review could have caught, because each task's own code is correct — the defect lived in what accumulates across runs. Both were in publication: the crosswalk other government systems join against.

R48 A published merge could never be withdrawn governance my spec gap

Nothing in the entire backend deleted from the crosswalk — publication was insert-or-update only. Everything upstream is recomputed each run; only this table accumulated.

Failure scenario A steward records no match. The guard flags the cluster. Publication correctly writes nothing — and the earlier run's rows still say those two people are one person. The verdict reaches scoring and never reaches the published product. The same held for a raised threshold, a deleted source row, and a cluster that split back into singletons, which never re-enter the crosswalk at all.

Resolution: publication now replaces rather than accumulates, in one transaction. Sound because every run reloads the full source, so the latest run's conclusions are the complete current picture. A run that publishes nothing still withdraws — "no duplicates found" is a conclusion, not an absence of one.

R49 · R60 A steward's correction could merge more records, not fewer governance

Entity keys were resolved by majority vote over existing crosswalk rows, with no record of what the same run had already assigned — so two clusters could claim one key.

Failure scenario A steward splits an over-merged entity. The larger fragment keeps the key by majority; the smaller fragment votes for it too. Both publish under the same key — more merged than before the steward intervened, as a direct result of their correction.

Resolution: a key is claimed once per run, and the largest fragment keeps it. I overruled the implementer here: it argued the tie-break was arbitrary, but fewest-published-identities-change is a real correctness criterion for a key other systems join on. Under the old rule a five-record split churned four identities; now it churns one.

R50 · R59 Dates shifted a day earlier — and the test for it did nothing in UTC silent corruption

Date normalization round-tripped through UTC. In Kigali, the deployment timezone, a date column holding 1990-01-01 became 1989-12-31 — the year changes, so the blocking key changes, so the duplicate is never proposed. No gate caught it because the test fixture declared that column as text.

The second failure, one layer up After the fix, the re-review restored the bug and ran the tests under five timezones: UTC gave zero failures (Kigali 7, Tokyo 14). Nothing pinned the timezone, so both gates were no-ops in any container — which is what CI runs. The same defect shape as the original: a test passing by sidestepping the hazard. The string branch also still shifted, reachable on SQLite, whose canonical date storage is exactly the affected format.

Resolution: the deployment timezone is now pinned in both test configs, with a guard asserting the offset is non-zero so the pin cannot be silently dropped. A counterfactual mutation proved it: with the pin, restoring the bug fails 7 tests in UTC; without it, only 3 — every day-shift assertion had been passing vacuously.

Governance and the legal boundary

Rulings about what the system is permitted to copy, who may act on it, and what it may claim.

Governance rulings — the allow-list, authority, and refusals
RulingDecision and reason
P4 · R10my defectThe primary key must appear on the column allow-list like any other column; the setup wizard adds it automatically. The allow-list is the auditable record of every column the feature may touch — if the reader silently adds a column, the record stops matching what was read, and the one rule an auditor can check stops being true.
R11 · R13Matching refuses Snowflake, BigQuery, ClickHouse and MongoDB sources. Four of nine drivers ignore bound parameters — MongoDB is not a SQL engine at all. Phase 1 supports five connection types plus staged data, and refuses the rest with a named reason rather than silently interpolating values into SQL.
R34Repeat deletion returns success, not conflict. A retry after a network timeout must not report a conflict; substantively a second delete copies no data and changes no authority. "Every mutating route" means every route that acts on data or authority, not every HTTP verb that writes.
R39my defectThe review queue is served both records and the per-field scores. As planned it had neither — a steward would have been shown two opaque keys and asked to certify a match. Where the workspace copy is gone, records return null and the queue collects no verdict: an unseen pair must never be certifiable.
R36my defectThe wizard's size estimate refuses cleanly before a project's first run rather than materializing on demand. Materializing copies citizen data, and the wizard records the lawful basis one step later — copying data to answer a question about size would invert the authority-then-data order the feature is built around.
P5my defectThe project edit and delete endpoints gain callers in the UI. They had none anywhere in the plan, and a user who cannot delete a project holding copied citizen data is a governance gap, not a usability one.

Correctness at scale

The plan targets ten million rows per side. These rulings are where code that is correct on three rows fails on ten million.

Scale and correctness rulings — all found before production
RulingDecision and reason
R21The trigram join must emit the % operator alongside the similarity test. Only % maps to the index the materializer builds; the similarity function alone cannot use it, so the planner falls back to a full cross-product — a correct result that never returns, invisible to any assertion on SQL text. Verified by query plan against a live database.
R22The key histogram aggregates server-side. Returning one row per distinct key means ten million rows buffered plus a second ten-million-object array in memory — gigabytes of heap, dying on exactly the input size it was written for.
R23my defectScoring must keep any pair carrying a human verdict, regardless of its score. Filtering on score alone drops the pair before the decision join can honour it — and stewards confirm precisely the pairs the score is unsure about, so confirmed pairs skew low-scoring by construction. The filter discarded human verdicts exactly where they carry the most information.
R26The over-merge guard reads decisions as well as scores. Once R23 began storing human-decided pairs regardless of score, a steward-confirmed pair could sit below the threshold — so the guard would flag a cluster as over-merged because a human confirmed it, withholding that match from the crosswalk.
R19The degenerate-key threshold becomes max(50, 0.5%). On a thousand-row table a bare 0.5% discards a surname shared by six people — ordinary data, lost invisibly. A key with fifty rows contributes 1,225 pairs, nothing against the cap, so excluding it buys no protection and costs recall.
R2 · R3Every comparator returns a number in [0,1], and one presence guard wraps all of them. Three findings shared one root cause: an empty string cast to a date aborts the whole query, null comparators poison the summed score so the pair falls out of both sides of the grey band silently, and two records that both lack a phone number scored as identical on that field.
R15The reader's page ceiling is 100,000 rows, and my reasoning-by-analogy was wrong. The limit I copied caps what an ad-hoc query hands to a browser; this is an internal batch loader whose pages never reach a user.

Where it stands

What is finished, what was deliberately left, and what needs your decision.

All gates green at HEAD

583 backend unit tests, 19 integration tests against live PostgreSQL, type-check clean, frontend build and lint clean, and the migration reverts and re-runs cleanly. The engine's own quality is unchanged through every fix: precision and recall 1.0000 against the seeded fixture, all 300 planted duplicates sharing an entity key.

That figure is not an accuracy claim. The fixture's perturbations — swapped name order, one-character typos, transposed birth-date digits — are exactly the cases the comparators were designed for. It proves the pipeline executes correctly end to end, not that it will perform this way on real registry data.

Both items previously marked required are now fixed

  • The docstring that claimed an invariant the code did not hold has been corrected, and the reasoning for the deliberate exception now lives in the code — with a tripwire noting what would have to change if anything non-repeatable is ever added to that method. It previously existed only in a working file that is deleted when the plan finishes.
  • The bound-parameter budget that sat exactly on PostgreSQL's 65,535 limit now reserves headroom, matching its sibling files.

Deliberately deferred — recorded, not forgotten

  • No evaluation surface. The precision/recall sweep and gold-set API are fully built and have zero callers, because there is no UI to manage a gold set. Building one is a task, not a fix. What I did fix was the wizard telling operators to set thresholds from numbers the product cannot show them. This is the first phase-2 item.
  • No frontend test infrastructure exists in this repository — no runner, no specs anywhere. The most serious review-queue defect found was exactly what a frontend test would pin. Standing one up is a project decision, not something a fix round should improvise.
  • Two rules are hand-duplicated across the codebase — the source-reference format in three places, the comparator-ordering rule in three. Accurate today; drift would fail silently. This is the same class as the defect that cost most on this branch.
  • The review queue re-serves pairs that already carry a verdict. Harmless, since a second verdict overwrites the first, but wasteful; honest filtering needs a count the API does not expose.
  • Smaller: the reviewer-role permission is unimplemented; dropped blocking keys and the job-size warning have no visible surface; the source can still be repointed after runs exist.

One thing to decide

Phase 1 supports five of the nine connection types, plus staged data. Snowflake, BigQuery, ClickHouse and MongoDB are refused with a named reason, because four of those drivers ignore bound parameters — a pre-existing defect in shared code, not something this branch introduced. Fixing them means threading each vendor's own binding API and testing against three hosted services. Whether that is phase-2 work or stays refused is a scope call that is yours, not mine.

Every ruling on this page is reversible. Each was recorded with its reasoning and its cost if wrong at the moment it was made, not reconstructed afterwards. Where I judged wrongly, the cost is rework you can see and undo.
