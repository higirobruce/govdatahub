DataGate Docs · Design, awaiting sign-off

One entity, many records.

A single matching engine with two entry points — deduplicate one dataset, or link the same person or business across two. It publishes a durable entity_key crosswalk, which is the join key Cross-Query has never had. Small language models run on a 16 GB CPU-only server and sit at the edges of the pipeline, never in the hot path.

What you are signing off

Four answers shaped this

You set the constraints during the brainstorm. Everything below follows from them, and a change to any one of them changes the design.

Scope

One engine, deduplication first

Build the cascade once. Ship single-dataset deduplication as phase 1, then add cross-dataset linkage on the same foundation.

Sources

Connections and Staged Data

Both, behind one interface. This is what pushed the design toward a materialized workspace rather than per-dialect SQL.

Scale

10M+ rows per side

National-register scale. This single answer is why no model touches the pair set, and why rejected pairs are never stored.

Hardware

CPU now, GPU later

16 GB, no GPU. Every model call stays behind the existing IAiProvider seam, so a GPU becomes a settings change rather than a rewrite.

This reverses an earlier call, deliberately. The September improvement review parked master data management as out of scope — "leave it to the Hub, consume golden records via API". The reason to reverse it is narrow and specific: cross-database joins are DataGate's strongest feature, and on government data they are close to unusable, because no two agencies share a join key. A crosswalk is that key. This is not full MDM — no stewardship-of-record, no golden-source arbitration across government. It is the one table the analytics layer needs in order to work at all.

The constraint that shapes everything

Why the model cannot read the pairs

Ten million rows against ten million rows is one hundred trillion pairs. A 1.7B instruct model on CPU needs four to six seconds per pair. The gap is not close, and no amount of engineering closes it — so the design routes around it.

Bar width is proportional to the base-10 logarithm of the pair count. On a linear scale every bar below the first would be invisible.

Three rules fall out of this and are not negotiable inside the design:

  • Everything up to and including scoring is SQL. No model, and no per-pair work in Node.
  • The instruct model runs only on pairs a person opens, one at a time.
  • No part of the design may assume a model sees a whole run's pairs.

What the model is actually for. Its contribution is not accuracy — the SQL comparators are more accurate and a thousand times faster. Its contribution is the written reason attached to a pair. A data steward can defend a sentence in an audit. A similarity score of 0.83 is much harder to defend. So the model explains, and never merges anything on its own.

Architecture

A materialized match workspace

One source abstraction reads either a live Connection table or a Staged Data dataset, and copies only the project's allow-listed columns into per-project tables in a matching schema inside DataGate's own PostgreSQL. Every stage after that runs there, in one dialect, with full extension access.

OptionApproachWhy not
A Push blocking SQL down into each source database Per-dialect blocking SQL across nine drivers, and MySQL has no trigram index. It also asks an agency's production database to run a 200-million-pair join — a political problem as much as a technical one.
B Stream rows into Node with an on-disk key index One implementation for every source, and the comparators would be pure and easily tested. But 200 million pairs through Node is hours where PostgreSQL is minutes, and it reimplements what the database already does well.
C Materialize allow-listed columns into a per-project workspace Chosen. The blocking and scoring SQL is written once; Connections and Staged Data become interchangeable to the engine; source databases only ever serve simple ordered reads.

Two findings from the code that changed the design

drivers/database-driver.interface.ts:38

No cursor, nine drivers

DatabaseDriver.query() returns every row in one in-memory array. Adding streaming to nine drivers is out of scope, so the materializer pages by keyset — WHERE pk > $last ORDER BY pk LIMIT 50000. Ten million rows is 200 round trips, and no driver changes.

A 40 GB table avoided

Rejected pairs are never stored

At 200 million candidates and ~200 bytes a row, storing every pair is a 40 GB table. One INSERT ... SELECT per pass scores and writes only rows at or above the reject threshold. Rejects are counted into the run, then dropped. The table stays in the low millions.

The honest cost of option C. It copies personal data into DataGate's own database. That is a real exposure, not a theoretical one, and it is only acceptable with the controls in the governance section below. Those controls are requirements of the design, not recommendations attached to it.

The engine

Five stages

A new backend module, packages/backend/src/modules/matching/, with one orchestrator and a service per stage.

  1. Materialize

    Read via connectionsService.getDriver() or from Staged Data. Keyset pages of 50,000 rows, written with COPY. Reads only the allow-listed columns — the single place that rule is enforced. A watermark on the run makes the next run incremental.

  2. Normalize

    Deterministic first, as pure functions: case, accents, whitespace, punctuation, ISO dates, phone numbers reduced to their last nine digits. Model normalization is limited to organization names and addresses — those have thousands of distinct values and benefit greatly from parsing. Person names do not need it: a token sort plus a phonetic key handles name-order variation, and a national register holds on the order of a million distinct names, far beyond a CPU model's budget. Everything is cached in match_norm_cache permanently.

  3. Block

    Each pass is one generated key column with an index behind it: surname phonetic plus birth year, last nine phone digits, surname phonetic plus district, a trigram join on the full name, and a pgvector pass over the distinct-value dictionary for organization names and addresses. Passes are joined independently and unioned.

  4. Score

    One statement per pass. Comparators run in SQL by role — trigram similarity and bounded edit distance for names, a token-set check for swapped name order, day difference and digit-transposition for dates, last-nine plus edit distance of one for phones and identity numbers. Pairs already carrying a human verdict take that answer and skip scoring.

  5. Cluster

    Union-find over pairs above the match threshold plus confirmed pairs, then write the crosswalk. Three rules matter more than the algorithm — they are below.

Two guards inside blocking

Both are part of the stage, not optional extras, because at this scale either one failing turns a one-hour run into a stalled one.

Guard 1

Estimate before running

Sample the key columns, build a frequency histogram, project the pair count per pass. The wizard shows the projection before anything runs. Above the configured cap it warns; above twice the cap it refuses.

Guard 2

Drop degenerate keys

Any key value covering more than 0.5% of rows makes its join quadratic. An empty surname does exactly this. Such values come out of the same histogram and are excluded, and the run records which ones were dropped.

Three rules inside clustering

RuleWhat it prevents
Over-merge guardAfter clustering, every pair inside a cluster is checked. If any internal pair falls below the reject threshold, the cluster is flagged and routed to review instead of published. This stops the "A matches B, B matches C, A does not match C" chain that silently merges unrelated people.
Stable entity keyOn a re-run, a cluster keeps the key held by the majority of its previous members; a genuinely new cluster gets a fresh one. Without this rule the crosswalk churns on every run and every downstream join breaks.
Survivorship with provenanceGolden-record rules per field — most recent, most complete, source priority, most frequent — and every golden field records the source and key its value came from. The model may write a prose explanation on request; it never chooses the value.

Data model

One migration, four entities, five tables

Migration 1711000000010-AddEntityMatching.ts adds pg_trgm and fuzzystrmatch in the same style as the existing vector and postgres_fdw migrations, and creates the matching schema.

Entities

All follow repository convention — text primary keys with uuidv4, JSONB for structured fields, organization_id on every row.

EntityPurposeNotable fields
MatchProjectThe configurationmode (dedupe or link), left and right source, field map with roles and weights, blocking passes, thresholds, column allow-list, lawful basis, data owner, retention days

MatchDecisionA person's verdict. Permanent.The pair, the verdict, who and when, and the score and model verdict that stood at the time

Why decisions live apart from candidates. Candidates belong to a run and expire with it. A human verdict is permanent, and it does three separate jobs: it is the audit trail, the next run reuses it instead of asking the same question again, and the accumulated verdicts become the labelled set that threshold tuning and the phase-4 weight model both require.

Plain tables, written by SQL

These follow the catalog_embeddings precedent — raw parameterized SQL, no TypeORM entity — because they are written in bulk by set-based statements.

TableRole
match_candidatesThe pair table. bigserial rather than uuid, because there are millions of rows. Decision takes exactly four values — auto_match, grey, confirmed, rejected. There is no auto_reject, because those pairs are never written.
match_crosswalkThe product. Maps source and source key to entity key, unique per project. This is what Cross-Query joins against.
match_norm_cacheNormalized values keyed by organization, role and raw value. This is what makes model-based normalization affordable.
match_value_vectorsThe distinct-value embedding dictionary behind the vector blocking pass. 384 dimensions, HNSW index, organization names and addresses only — never one row per record.
match_gold_pairsHand-labelled pairs, per project. The evaluation set.
matching.p_<id>_left/_rightThe workspace. One column per mapped field holding the normalized value, plus a generated column and index per blocking pass. Dropped by retention.

Models and budget

Three tiers, each cheaper per pair than the last

TierWhat runsPairs it seesSpeed
1SQL string metrics — trigram, edit distance, phonetic~2 × 108minutes for the whole set
2Cross-encoder reranker phase 4the grey band~100 per second
3Small instruct model — writes the reasononly pairs a person opens~5 seconds each

Tier 3 defaults to Qwen3-1.7B at Q4 — about 1.1 GB resident, good JSON adherence, multilingual. It is called through the existing IAiProvider.generateJson() and returns a match flag, a confidence, and a reason. A model failure leaves the pair unannotated rather than failing the run.

One settings change is needed. generateJson() reads settings.aiModel, which on the RISA setup is the 30B chat model. Matching needs a small one, so add aiSmallModel to organization settings. The error doctor and the check suggester can use it too.

Why the reranker waits for phase 4

A cross-encoder is the most specialized small model in this design and the right tool for the grey band: one forward pass, no text generation, roughly a hundred pairs a second, which turns a 200,000-pair band into something a team can finish. But Ollama does not serve rerankers well, so it needs one new container. Version 1 therefore adds zero new services, and the adjudication service carries a scorePairs() seam so the reranker slots in later without a rewrite.

It fits, tightly. The 30B chat model must not run on this box — it needs about 20 GB. Disk is roughly 15 to 20 GB per large project once workspace columns, indexes and surviving candidates are counted, so retention has to reclaim it.

Estimated run time for 10M × 10M, to be confirmed on the real hardware: materialize 20–60 minutes, block and score 10–40 minutes, cluster a few minutes. One to two hours, with no model in the hot path.

The review queue

This is where a data steward spends the day, and it is the screen the feature succeeds or fails on.

Two record cards side by side, aligned field by field. Each field carries a similarity bar and has its differing characters marked. The overall score and the blocking pass that proposed the pair are both shown, so a reviewer can see why the pair arrived. The model's reason loads when the pair opens — about five seconds, with a skeleton in the meantime.

Keys: m match, n no match, s skip, u undo, j and k to move. The queue orders pairs by decision value — nearest the threshold first, where a human answer carries the most information. Every keystroke writes a permanent decision.

Governance

Six rules, all requirements

The data is citizen and business personal data. Rwanda's Law No. 058/2021 on personal data protection and the National Data Sharing Policy of May 2025 both bear on it directly.

  1. The materializer reads only allow-listed columns

    One rule, one place in the code, covered by a test.

  2. A matching project refuses a remote AI provider

    Local, or custom pointed at a private host, only. The code throws on OpenAI, Anthropic and Azure. Personal data never leaves the server — which is the whole reason small local models matter here rather than being a preference.

  3. Lawful basis and data owner are required fields

    Non-empty, on every project. Not metadata to fill in later.

  4. Roles guard every mutating endpoint

    Review is its own role. The repository audit found @Roles guarding zero endpoints today, finding SEC-10. Matching must not repeat that.

  5. Every model call is audited

    Through the existing audit service, under matching_align, matching_normalize and matching_adjudicate. It stores sizes and metadata, never record values, matching the contract that service already keeps.

  6. Workspace data is encrypted at rest and expires

    A daily cleanup job, modelled on the transformations cleanup service, drops workspace tables and candidate rows past their retention. Decisions, clusters, the crosswalk, the gold set and the normalization cache survive — they are results and audit, not working data.

Evaluation

Thresholds you can defend

An evaluation service reads the hand-labelled gold pairs and reports precision, recall and F1 at the current thresholds, plus a sweep across thresholds so the operating point is chosen deliberately. The wizard's threshold step calls it. Confirmed and rejected pairs from the review queue can be promoted into the gold set, so the measurement improves as the queue is worked.

This is part of the feature, not an extra. Without a gold set the thresholds are a guess, and a guess cannot be defended when someone asks why two citizen records were merged.

Order of work

Four phases, and the plan covers the first

PhaseContent
1Deduplicate one source. Materialize, deterministic normalize, block, score, cluster, review queue, crosswalk, the no_duplicates check. No model except field alignment. Useful on its own, and it proves the engine before any model is trusted with anything.
2The models. Lazy adjudication with written reasons, model normalization for organization names and addresses, the vector blocking pass and its dictionary, model-suggested field mapping in the wizard.
3Linkage across two sources. Right source, cross-source clusters, golden record and survivorship, Cross-Query integration, lineage edges.
4Quality. The reranker tier, Fellegi–Sunter weights estimated from the collected labels, incremental re-match, the match pipeline step.

The implementation plan that follows covers phase 1 only. Phases 2 to 4 each get their own plan, written after phase 1 has run on the target box and the timing estimates above have been replaced with measurements.
