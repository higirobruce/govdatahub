Building it.

Engineering plan for the three visualization milestones from the benchmark. Specifies entities, migrations, services, components, sequencing, and acceptance criteria — enough for a single engineer to start the day and ship the right thing.

Scope

Goals & non-goals

Goals

  • Reach feature parity with Metabase and Superset on the dashboard surface that most users see in the first session.
  • Preserve DataGate's cross-database query advantage by routing all new features through the existing FDW layer.
  • Avoid heavy rewrites — extend existing modules (queries, dashboard, pipelines) rather than introducing parallel systems.
  • Keep every change shippable on its own. No twelve-week branches.

Non-goals

  • A full Metabase-class question builder. M3 ships a lightweight version only.
  • Machine-learning anomaly detection. Threshold alerts only in M2.
  • White-label theming or marketplace plugin model. Out of scope for this round.
  • Replacing ECharts. All new chart types extend the existing renderer.
Note

This plan assumes the benchmark (docs/visualization-benchmark.html) and the feature overview (docs/data-visualization.html) as context. Read those first if you're picking this up cold.

Architecture

Moving parts

The plan introduces one new cross-cutting layer (the template engine) and two new modules (delivery, embed). Everything else extends existing modules.

Boxes in azure are introduced by this plan; white boxes are existing modules being extended or reused.

Sequencing

Ticket-level timeline

Each milestone has a critical chain plus a handful of independent tickets that can run in parallel. The chart below shows when each ticket starts and ends in a 24-week plan, and which bars sit on the critical path. Bars are sized by effort estimate.

Critical chain

The sequence that determines total elapsed time, in order:

  1. F-01 template engine → M1-01 parameterized queries → M1-02 dashboard filters → M1-03 cross-filter on click. (M1 closes when M1-03 lands; M1-04/05/06/07/08 can finish earlier and wait.)
  2. M2-01 snapshot renderer → M2-02 subscriptions → M2-03 alerts. (M2-04 and M2-05 are independent.)
  3. M3-01 embed JWT → M3-02 row-level security. (M3-03/04/05/06 are independent; M3-06 is the longest tail.)

Parallelization notes

  • Foundations — F-01 and F-02 are independent and can land in the same week if two engineers split them.
  • Inside M1 — once F-01 ships, M1-01 begins, but the widget tickets (M1-04, M1-05, M1-06, M1-07, M1-08) don't depend on it and can be picked up by anyone in parallel.
  • M2 ↔ M3 overlap — M3-01 needs F-01 (already shipped) and depends on the snapshot renderer's auth path landing in M2-01. A small engineering team can start M3-03 (saved metrics) during M2 since it has no M2 dependencies.
  • Bottleneck — M3-06 (question builder) is the longest single ticket. Splitting it into smaller sub-tickets (source picker, summarize step, group-by step, filter step, visualize handoff) lets it run with more parallelism.
Tip

The critical chain hits 21 weeks; the milestone target of 24 weeks gives a 3-week buffer for QA, design polish, and unforeseen rework. If a foundation slips by more than a week, expect a one-to-one slip in the GA date.

Foundations

Two pieces of plumbing first

Both unblock the bulk of M1. Land them in order, then everything else parallelizes.

F-01

Query template engine

Effort: M

Single source of truth for {{param}} substitution. Used by saved queries, dashboard filters, scheduled subscriptions, and embed-mode parameter overrides.

Backend
  • New service packages/backend/src/modules/queries/query-template.service.ts with render(sql, defs, values, allowedIdentifiers): { sql, bindings }.
  • Two substitution modes:
    • Value (default): {{date}} → $1 in SQL; value goes into the bindings array. Driver does the binding.
    • Identifier: {{!table}} → double-quoted identifier, whitelist-validated against known schema names from the connection.
  • Reject any token not matching ^[a-zA-Z_][a-zA-Z0-9_.]*$.
  • Parameter types: 'string' | 'number' | 'boolean' | 'date' | 'date_range' | 'select' | 'multi_select'. date_range expands to two bound values: {{range.start}}, {{range.end}}.
  • Export from QueriesModule so other modules can consume.
Code skeleton

The contract below is the load-bearing piece — it's the line between safe and unsafe SQL. Value mode always binds via the driver; identifier mode always goes through the allow-list. There is no third mode.

// packages/backend/src/modules/queries/query-template.service.ts
import { Injectable, BadRequestException } from '@nestjs/common';

export type ParamType =
  | 'string' | 'number' | 'boolean' | 'date'
  | 'date_range' | 'select' | 'multi_select';

export interface ParamDef {
  name: string;
  type: ParamType;
  required: boolean;
  default?: unknown;
}

export interface RenderResult {
  sql: string;
  bindings: unknown[];
}

// Two-character mark, optional identifier flag, then a dotted accessor.
const TOKEN_RX = /\{\{\s*(!?)\s*([a-zA-Z_][a-zA-Z0-9_.]*)\s*\}\}/g;
const IDENT_RX = /^[a-zA-Z_][a-zA-Z0-9_]*$/;

@Injectable()
export class QueryTemplateService {
  render(
    sql: string,
    defs: ParamDef[],
    values: Record<string, unknown>,
    allowedIdentifiers: Set<string>,
  ): RenderResult {
    const defsByName = new Map(defs.map(d => [d.name, d]));
    const bindings: unknown[] = [];

    const rendered = sql.replace(TOKEN_RX, (_match, identMark, accessor) => {
      const isIdent = identMark === '!';
      const rootName = accessor.split('.')[0];
      const def = defsByName.get(rootName);

      if (!def) {
        throw new BadRequestException(`Unknown parameter "${accessor}"`);
      }

      const raw = this.resolveValue(def, values, accessor);

      if (isIdent) {
        // Identifier mode: never bind, only whitelist.
        if (typeof raw !== 'string' || !IDENT_RX.test(raw) || !allowedIdentifiers.has(raw)) {
          throw new BadRequestException(`Identifier "${raw}" not in allow-list`);
        }
        return `"${raw}"`;
      }

      // Value mode: ALWAYS bind, never interpolate.
      bindings.push(raw);
      return `$${bindings.length}`;
    });

    return { sql: rendered, bindings };
  }

  private resolveValue(def: ParamDef, values: Record<string, unknown>, accessor: string) {
    // Walks dotted accessors (e.g. range.start), applies defaults,
    // enforces type, rejects missing-required. Implementation omitted.
  }
}
Required tests (CI must cover)
// queries/query-template.service.spec.ts — load-bearing fixtures
describe('QueryTemplateService', () => {
  it('value mode binds, never interpolates', () => {
    const r = svc.render('SELECT {{x}}', [{ name: 'x', type: 'string', required: true }],
      { x: "1; DROP TABLE users; --" }, new Set());
    expect(r.sql).toBe('SELECT $1');
    expect(r.bindings).toEqual(["1; DROP TABLE users; --"]);
  });

  it('identifier mode rejects non-whitelisted values', () => {
    expect(() => svc.render('SELECT * FROM {{!t}}',
      [{ name: 't', type: 'string', required: true }],
      { t: 'users; DROP --' }, new Set(['orders'])))
      .toThrow(/not in allow-list/);
  });

  it('rejects unknown parameters', () => {
    expect(() => svc.render('SELECT {{ghost}}', [], {}, new Set()))
      .toThrow(/Unknown parameter/);
  });

  it('date_range expands to two bindings', () => {
    const r = svc.render('WHERE d BETWEEN {{r.start}} AND {{r.end}}',
      [{ name: 'r', type: 'date_range', required: true }],
      { r: { start: '2026-01-01', end: '2026-03-31' } }, new Set());
    expect(r.bindings).toEqual(['2026-01-01', '2026-03-31']);
  });
});
Security

Reviewer checklist for any PR that touches this file: (1) every replace path either binds via bindings.push or routes through the allow-list — never both bypassed; (2) no string concatenation of user-supplied values into the rendered SQL; (3) the identifier allow-list is sourced from live schema discovery, not user input.

Acceptance criteria
  • Unit tests cover injection attempts ('); DROP --, {{a}}; DROP, identifier mode with non-whitelisted value).
  • Saved query with WHERE created_at > {{since}} executes correctly when called with { since: '2026-01-01' }.
F-02

Query result cache (Redis-backed LRU)

Effort: M

Used by widgets to avoid re-running queries on every dashboard open. Foundation for delivery (M2) and embed (M3) too.

Infra
  • Add Redis to docker-compose.yml (latest stable, single-node, password-protected).
  • Env: REDIS_URL. Health check on startup.
Backend
  • New module packages/backend/src/modules/cache/ with QueryCacheService.
  • Key: sha1(orgId + connectionId + renderedSql + bindings); namespace under qcache:.
  • Value: { rows, columns, executedAt, durationMs } with default TTL 300s; override per saved query via new cache_ttl_seconds column.
  • Wrap the existing query executor: cache-aside read; on miss, execute and write.
  • Explicit purge endpoint: POST /api/queries/:id/cache/purge.
Acceptance criteria
  • Second open of the same dashboard within TTL is observably faster (timing log shows cache hit).
  • Editing a saved query bumps its cache namespace; old entries become unreachable, not stale.
Milestone 1 · ~6–8 weeks

Interactive dashboards

Make dashboards feel alive. After M1 a user can filter, click to drill, see a big number with a delta, and pin a markdown note. F-01 and F-02 must be merged before starting.

M1-01

Parameterized saved queries

Effort: M

Saved queries declare a typed parameter schema. The query editor renders inputs for them. Execution routes through QueryTemplateService (F-01).

Migration
ALTER TABLE saved_queries
  ADD COLUMN parameters jsonb NOT NULL DEFAULT '[]',
  ADD COLUMN cache_ttl_seconds int NOT NULL DEFAULT 300;

Shape of parameters: Array<{ name, type, default?, required, label? }>.

Backend
  • Extend SavedQueryEntity with the new columns (JSONB pattern: @Column('jsonb', { default: [] })).
  • Extend POST /api/queries/execute to accept { savedQueryId, parameters }. Validate parameter values against the declared schema before passing to the template engine.
  • Re-run all existing saved-query callers through the new path; an empty parameter list is a no-op.
Frontend
  • Saved-query editor (packages/frontend/app/query/): a new "Parameters" tab to declare them.
  • Generic <QueryParameterInput /> that renders by type (date picker, select, text…). Reuse in widget config and embed renderer.
Acceptance criteria
  • A saved query with one date parameter runs end-to-end from the editor with a chosen value.
  • Bad parameter values (wrong type, missing required) return 400 with a per-field error map.
M1-02

Dashboard filters

Effort: M

A filter bar above the grid. Each filter has a name and feeds zero or more widget parameters. State lives in URL query params so a filtered view is shareable.

Migration
ALTER TABLE dashboards
  ADD COLUMN filters jsonb NOT NULL DEFAULT '[]';

Each widget's existing config gains parameter_bindings: Record<saved_query_param_name, dashboard_filter_name>.

Backend
  • Dashboard render endpoint receives filter values, resolves the binding map per widget, executes each widget's query with the resolved parameters.
  • Unbound parameters fall back to their declared default.
Frontend
  • New <DashboardFilterBar /> rendered above DashboardGrid. Filter chips with inline editors.
  • Filter state stored in URL via useSearchParams and propagated via context.
  • Widget config gains a "Parameter bindings" tab that lists the widget's saved-query parameters and a dropdown of dashboard filters per row.
Acceptance criteria
  • Adding a date-range filter, binding it to three widgets, and changing it once re-renders all three with the same range.
  • Reloading the page with a filter URL parameter restores the same filtered state.
M1-03

Cross-filter on click

Effort: S

Frontend

Milestone 2 · ~6 weeks

Delivery & performance

Get dashboards out of DataGate and in front of people, fast. After M2 a dashboard can be cached, exported as a PDF, scheduled to a Slack channel, or set to alert on a threshold.

M2-01

Dashboard snapshot renderer

Effort: M

Headless render of a dashboard to PDF, PNG, and CSV. Foundation for delivery and on-demand export.

Backend
  • New module packages/backend/src/modules/delivery/ with SnapshotService.
  • PDF/PNG: spawn Puppeteer (or call an existing catalog-screenshot binary if present), navigate to the embed-mode URL (depends on M3-01 partial — ship a temporary signed-token issuance scoped to internal renderer use).
  • CSV: per-widget, dump the underlying query result. Combine into a zip for the dashboard-level export.
API
  • POST /api/dashboards/:id/snapshot → { format, filters? } → returns a download URL.
Frontend
  • Toolbar adds an "Export" menu with PDF, PNG, CSV.
M2-02

Dashboard subscriptions (scheduled delivery)

Effort: M

Send a snapshot on a cron schedule to email or Slack. Reuses @nestjs/schedule + the snapshot renderer.

Migration
CREATE TABLE dashboard_subscriptions (
  id              text PRIMARY KEY,
  dashboard_id    text NOT NULL REFERENCES dashboards(id),
  organization_id text NOT NULL,
  schedule_cron   text NOT NULL,

Frontend

Milestone 3 · ~8 weeks

Embed & semantic layer

Open the door to embedded analytics and reusable metrics. After M3 DataGate can be dropped into another product behind a signed token, and analysts can name a metric once and reuse it everywhere.

M3-01

Signed-JWT embed mode

Effort: M

External host app obtains a short-lived JWT scoped to a dashboard + parameter overrides, then iframes DataGate.

Backend
  • New module packages/backend/src/modules/embed/.
  • POST /api/embed/token (machine-to-machine, separate API key) → { dashboardId, parameters, ttlSeconds, userContext? } → signed JWT.
  • Embed routes accept the token via query string or Authorization header.
  • Token claims pin the dashboard, parameter overrides (cannot be changed in-app), and an optional user context for RLS (M3-02).
Frontend
  • New route /embed/[id] renders the dashboard without app chrome (no sidebar, no top bar). Honors only the parameters the token allows.
  • Documentation page with copy-paste iframe snippet and a Node example for token issuance.
M3-02

Row-level security on shares

Effort: L

An RLS predicate is injected into every widget query for a shared dashboard. The predicate is templated against the recipient identity.

Migration
ALTER TABLE saved_queries
  ADD COLUMN rls_predicate text;   -- e.g. region = {{user.region}}
Backend
  • Query executor: when called via embed/share with a user context, AND the predicate into the WHERE clause via the template engine.
  • Refuse to execute if the predicate references a missing user attribute (no implicit unsafe fallback).
Acceptance criteria
  • Same dashboard, different embed tokens with different user contexts, see different rows — verified with a unit-test fixture that asserts SQL diffs.
M3-03

Saved metrics

Effort: L

Named aggregates with a stable identifier. Widgets reference them instead of inlining SQL.

Migration
CREATE TABLE metrics (

  name            text NOT NULL,

Frontend
  • New /metrics page with CRUD.

M3-06

Lightweight question builder

Effort: L

A schema-aware UI: pick a table, summarize by an aggregation, group by, filter — generate SQL behind the scenes. Doesn't need to match Metabase's full surface; even a 60% version expands the addressable audience.

Backend

  • New POST /api/queries/build → { tableRef, summarize, groupBy[], filters[] } → returns generated SQL (does not save).
Frontend
  • New /explore route. Step-form UI: source → metric → grouping → filters → visualize.
  • "Save as saved query" hands off to the existing saved-query editor.

Operations

Rollout strategy

Every user-visible feature in this plan ships behind an organization-scoped flag and rolls out through four cohorts. The flag schema lives in organization_settings.feature_flags — already a JSONB column — so wiring up a new flag requires no migration.

Flag schema

// organization_settings.feature_flags shape
{
  "viz.parameters":    true,    // M1-01
  "viz.filters":       true,    // M1-02, M1-03
  "viz.kpi_tile":      true,    // M1-04
  "viz.pivot":         true,    // M1-05
  "viz.markdown":      true,    // M1-06
  "viz.auto_refresh":  true,    // M1-07
  "viz.annotations":   true,    // M1-08
  "viz.cache":         true,    // F-02
  "viz.delivery":      false,   // M2-02, M2-03
  "viz.async_queries": false,   // M2-04
  "viz.versions":      false,   // M2-05
  "viz.embed":         false,   // M3-01, M3-02
  "viz.metrics":       false,   // M3-03
  "viz.tabs":          false,   // M3-04
  "viz.geo_map":       false,   // M3-05
  "viz.explore":       false    // M3-06
}

Naming rule: viz.<short-feature>, snake_case after the dot. Each flag controls a feature surface, not a single ticket — tickets that ship together (M1-02 / M1-03 / templated saved queries) gate behind one flag.

Cohorts

Every feature walks the same path:

CohortDurationWhat happensGate to next
Dev Until merge Flag on for the dev org only. Engineering team builds and validates against the seed data. PR review + green CI
Internal 3–5 days Flag on for two internal orgs (datagate-team + datagate-finance). PM and design exercise the feature against real data. Bugs caught here cost a follow-up PR, not a hotfix. Zero P0/P1 bugs open
Canary 1–2 weeks Flag on for one consenting external org. Monitor error rates, query durations, and qualitative feedback. The org must know they're on the canary. No regression in core metrics for 5 consecutive days
GA Open-ended Flag flipped on for all orgs by default. The flag itself stays in the code for two stable releases as a kill-switch. Two minor releases with no flag-related incidents
Sunset One PR Flag removed from code. The feature is just part of the product now. —

Per-milestone rollout shape

  • Foundations (F-01, F-02) — no user-visible surface, but F-02 hides behind viz.cache so it can be disabled if cache invalidation bugs appear. F-01 is gated by being routed through opt-in saved queries: a saved query without parameters bypasses the engine entirely.
  • M1 — eight flags, one per widget/feature. Filters (viz.filters) is the most user-visible and goes to Canary last. Markdown, auto-refresh, and annotations can promote to GA quickly since they're additive.
  • M2 — delivery and async queries each carry incident risk (Puppeteer hangs, queue backups). Plan for one extra week in Canary for both.
  • M3 — viz.embed only goes GA after a paying customer has validated the host-app integration end-to-end. RLS (viz.embed_rls, gated under the same embed flag) cannot be canaried without a tenant whose data we can verify partitioned correctly.

Disable / kill-switch path

Each feature respects its flag in three places:

  1. Backend route guards return 404 when the flag is off for the caller's org. No silent partial-disable.
  2. Frontend feature components render null when the flag is off, and the nav entries / chart-type pickers omit the feature from the choices.
  3. Scheduled jobs (subscriptions, alerts) check the flag at execution time, not at registration time, so flipping a flag immediately stops future fires without needing to re-register.
Don't

Flag checks must never depend on caching the flag value in memory. If an org enables viz.embed at 09:00, the first POST /embed/token at 09:01 must succeed without a process restart. Read the flag from the database per request (the existing organization_settings SWR cache is short enough).

Migration safety

All migrations in this plan are additive (new columns with defaults, new tables, no column type changes). The rollback plan for each:

  • New columns with DEFAULT: rollback is ALTER TABLE … DROP COLUMN. Safe at any time.
  • New tables: rollback is DROP TABLE … CASCADE after disabling the corresponding flag for all orgs.
  • No data backfills are required by this plan. Any future plan that does require one must add an explicit "Backfill plan" section to its ticket.

Risk

Things that could go wrong

Risk · template engine

SQL injection via parameter substitution is the highest-blast-radius bug in this plan. Mitigation: value-mode parameters bind through the driver, never string-concatenate; identifier mode validates against an allowlist sourced from live schema discovery; fuzzing tests in CI.

Risk · embed RLS

A poorly written RLS predicate leaks rows across tenants. Mitigation: predicate references must resolve to a non-empty user attribute or the query is refused; integration test fixture asserts SQL diffs across user contexts.

Risk · Puppeteer in production

Headless Chromium is heavy and flaky in resource-constrained containers. Mitigation: run the renderer as a separate worker process behind the existing queue; provision dedicated memory; document fallback to per-chart PNG composition if PDF fails.

Risk · Redis dependency

A new infrastructure dependency adds a deployment failure mode. Mitigation: F-02 ships an in-process LRU fallback for solo-dev mode; Redis becomes required only when delivery or async queries are enabled.

Decisions needed

Open questions

  1. Should dashboard filters be globally cascading by default, or opt-in per filter? Metabase makes them independent; Superset makes them cascading. Lean independent for v1; reconsider after user feedback.
  2. For Puppeteer rendering: bundle Chromium inside the backend container, or call a separate worker service? Affects image size and ops surface.
  3. Embed token: rotate per-render (every iframe load fetches a new one) or longer-lived (hours)? Trade-off between security and host-app complexity.
  4. Saved metrics — do we need metric_dimensions as a separate concept (Superset model) or always derive group-bys from the widget? Start with the latter; revisit if calculations get repetitive.
  5. How aggressively to cache by default? 5 minutes is a safe start, but stale data on a "live ops" dashboard would surprise users. Consider a per-dashboard override.
