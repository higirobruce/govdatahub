Verdict

The short version

The engineering core is genuinely good — FDW cross-database queries, a hardened query-template engine, nine drivers, profiling, lineage, pipelines. But the platform is currently held back by three walls, and each one is fixable.

Wall 1 · Security

Not safe to deploy beyond your laptop

The entire ingestion API is unauthenticated with a hardcoded tenant ID, the URL importer is an open SSRF, transformations can be executed across organizations, and two SQL-injection paths exist. Until the two-week security sprint in the roadmap lands, DataGate must not face a network.

Wall 2 · Invisible work

Five commits of M1 dashboards are unreachable

The API-backed dashboard viewer (/dashboards/[id]) — filters, URL-synced state, cross-filtering — has no inbound link anywhere in the app. Users only ever see the old localStorage builder with fake sample data. One small PR unlocks all of it.

Wall 3 · AI in name only

"AI-ready" is currently ~1,500 LOC of latent capability

NL2SQL exists but is blind: an argument-order bug feeds the model an empty schema. Three of five advertised providers throw "not implemented". "Explain SQL" is built on both ends but wired on neither. No embeddings, no vector store, no semantic anything. The local GPU changes this story completely.

The opening

Timing favors you

Rwanda approved its National Data Sharing Policy (May 2025) and RISA is procuring the Shared Government Data Hub under RDAP — ingestion, cataloguing, governance, MDM and analytics layers. DataGate already covers three of those layers, and a fully local GPU-powered AI stack aligns exactly with the National AI Policy's data-sovereignty pillar.

AI · the GPU plan

AI across the whole tool

A local GPU changes the constraint that shaped the current design: inference is now free, private, and always available. Every byte stays on your machine — which is not just convenient, it is the posture Rwanda's National AI Policy and Data Sharing Policy actually call for in government data systems.

Foundation first (AI-1)

  1. Stand up local serving S

    Keep Ollama for development; adopt vLLM (OpenAI-compatible) when concurrent org users arrive. Add ollama as an optional docker-compose service with GPU passthrough so setup is reproducible, and replace the endpoint string-sniffing in the local provider with an explicit apiFormat setting.

  2. Rebuild the provider layer M

    One OpenAI-compatible client with streaming, timeouts, retries and structured (JSON-mode) output — this makes the fragile line-scanning response parser and the fabricated confidence scores (COR-09) obsolete, and gets Anthropic/OpenAI/Azure support nearly for free as remote fallbacks where policy allows.

  3. Feed the model a real schema M

    Fix COR-01, then populate the already-declared RelationshipSchema (foreign keys from information_schema) and sampleData (3 rows via the existing profiler). Relationships plus sample values are the two highest-impact inputs for text-to-SQL accuracy — the interfaces were designed for this and never filled.

  4. Add the semantic layer: pgvector + embeddings S

    One migration (CREATE EXTENSION vector) on the existing Postgres 15 metadata DB — no new infrastructure. An EmbeddingService batch-embeds table names, column names, descriptions and profile summaries on the GPU. This single index powers semantic catalog search, NL2SQL table selection, and join suggestions.

  5. AI audit table S

    Log every generation: user, org, prompt, model, latency, generated SQL, and whether it was executed. This is the governance record a government deployment will be asked for on day one, and it doubles as your evaluation dataset for improving prompts.

AI-0 (fixes) proves the story in a demo. AI-1 (foundation) is what everything else stands on — provider layer, real schema context, pgvector, audit. Adoption

From working software to adopted software

DataGate's adoption surface is nearly zero today: a first-run user lands in an empty app with no tour, no sample data, no help, English-only, and no way to invite a colleague. The features exist; the on-ramp doesn't.

Make it findable

Surface what's already built

Wire the M1 dashboards into navigation (PROD-01), restore /catalog and /dashboard-analytics to the sidebar, fix the /support 404, link the NL2SQL tab to settings, ship Explain-SQL. A week of small PRs makes the product feel twice as big — because it is.

First-run experience

Demo mode with a Rwandan dataset

Seed a demo connection with realistic public-sector-shaped data (districts, facilities, enrollment), a pre-built dashboard, and a 5-step guided tour ending on "ask a question in natural language". A demo mode is also your RISA pitch, packaged.

Language

Decide on i18n now

Kinyarwanda and French are hard requirements for broad government use, and the retrofit cost grows with every inline string (PROD-17). Adopt next-intl, extract strings incrementally starting with navigation and the query/dashboard pages. LLM-assisted first-pass translation (reviewed by a human) makes this cheaper than it used to be.

Teams

Invites, roles, and real multi-user

Adoption inside an institution means "add my colleague": build the invite flow, apply the existing-but-unused RolesGuard to mutating endpoints (SEC-10), and gate the destructive UI by role (PROD-12). Without this, every deployment is a single-user tool.

Installability

Deployment is an adoption feature

Nobody can run DataGate today without your laptop's setup (OPS-01). Two Dockerfiles, a prod compose profile (app + Postgres + Ollama), a health endpoint, and a CI pipeline running the existing tests turn "come look at my screen" into "here's the compose file".

Positioning

Speak to analysts, not engineers

The landing page sells FDW and AES-256-GCM (PROD-20). The buyer is a director of planning or an M&E lead; the message is "ask questions across all your institution's databases, in your language, on your own servers". Rewrite the landing copy around outcomes, keep the engineering under the hood.

Ecosystem

The RISA Data Hub fit

The context is unusually favorable. Rwanda's National Data Sharing Policy was approved in May 2025 (MINICT lead; NISR governs, RISA builds the platform). Under the World Bank-financed RDAP, RISA has been procuring the Shared Government Data Hub and Data Interoperability Platform — a 24-month implementation with layers for data ingestion, cataloguing, governance, master data management and analytics, plus X-Road-style secure API exchange between agencies.

An interesting historical note: this project literally began life as GovDataHub and was deliberately de-governmentalized in the rebrand. The ecosystem has now come back around to exactly that original thesis — and the tender's proposal deadline (May 2026) has passed, meaning an implementing firm is being or has been selected. DataGate's play is therefore not to be the Data Hub, but to be the best thing plugged into it — and, internally, the working demonstrator of what the analytics layer should feel like.

Three positioning moves

  1. The self-service analytics workbench on top of the Hub

    The Hub centralizes and governs; DataGate is where a ministry analyst actually connects, joins, asks questions and builds dashboards — in Kinyarwanda or French, on government infrastructure, with a local model. This is the durable role no interoperability platform fills.

  2. The internal demonstrator

    As the Data Hub implementation ramps up, a working, GPU-powered, fully local demo of "ingest → catalog → cross-query → ask in natural language → dashboard" is the most concrete artifact anyone at RISA can put in front of stakeholders to define what the analytics layer must achieve. Demo mode (adoption plan) is this, packaged.

  3. The sovereignty proof point

    Rwanda's National AI Policy pillars include compute infrastructure, public-sector adoption, and trustworthy AI. Every AI feature in this review runs on a local GPU with zero data egress — a compliance answer most vendor tools cannot give. Say so, explicitly, in the product and the pitch.

Prerequisite

None of these moves survive a security review in DataGate's current state. Phase 0 of the roadmap is not optional housekeeping — it is the entry ticket to any government conversation.

Roadmap

Sequenced plan

Four phases, each independently valuable, ordered so that every later phase stands on the one before it.

  1. Phase 0 — Security sprint ~2 weeks

    SEC-01 through SEC-11 plus COR-03/04: guard ingestion, kill the hardcoded UUID, SSRF protection, org-scope the executors, register global guards, hash tokens, apply RolesGuard, fix the dead DTOs. Add tests for exactly these paths (starts OPS-08). Exit criterion: the app can face a shared network.

  2. Phase 1 — Unblock what's built ~1 week

    PROD-01/05/06/08/09 + COR-01/06: dashboards list page linking to the API viewer, sidebar fixes, NL2SQL discoverable, Explain-SQL shipped, NL2SQL un-blinded. Plus the XS hygiene batch (lockfile, react-resizable, dead files, env drift). Exit criterion: everything that exists is reachable and demoable.

  3. Phase 2 — AI foundation + first features ~3–4 weeks

    AI-1 in full (serving, provider layer, schema context, pgvector, audit table), then the three cheapest high-visibility AI-2 features: semantic catalog search, error doctor, suggested quality checks. In parallel: M1-04 KPI tile and M1-06 markdown widget (both small) so dashboards round out.

  4. Phase 3 — Adoption & ecosystem ongoing

    Dockerfiles + CI + health checks; demo mode with Rwandan sample data; i18n rollout (rw/fr); invite flow; landing rewrite; then the AI-3 differentiators (ask-a-question dashboards, column-level lineage) and the RISA demonstrator pitch. M2 delivery features (subscriptions, alerts) slot in as pull demands.
